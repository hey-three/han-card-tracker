# 模型训练与固定画布拼图约定

更新日期：2026-10-27。本文区分当前代码、建议训练方案和待验证事项；讨论结论变化时同步 AGENTS、README 和对应设计说明。

## 已确定并实现的输入契约

- 拼图画布固定为 **640×640，宽高比 1:1，RGB，空白为 (114,114,114)**。
- 原图分辨率、相对区域、图块数量及排列可以变化，最终画布尺寸不变。不采用按游戏名称查表的区域模板。
- `core/frame_packing.py` 的 `make_plan()` 先在原始像素下选取紧凑排列，再调用 `.fit()`，将整套排列按一个共同倍率放入固定画布。各块不会各自随意放大，也不会把长条硬拉成方形。栅格宽高有不足一个像素的取整误差，恢复按实际绘制尺寸执行。
- 长条中心两侧有重叠保护。模型可能在两个图块中各检出同一张牌，必须用 `Tile.unproject()` 还原到原图后再去重；原图不同位置的同点数仍是多张牌。
- 检测落在灰边、跨图块、切口缺完整副本或同位置类别冲突时，回退当前同一张原图；不会发布半套结果。
- 调试图片仍保存原图及原图坐标标注；下面的彩框、编号只在讲解图出现，实际输入没有这些辅助线。

## 当前阶段调度

| 阶段 | 当前行为 | 边界 |
|---|---|---|
| 等待开局、换局 | 整图检测合法完整 17/20 张本家手牌和无出牌证据 | 尚未实现只用下半屏完成开局校准 |
| 开局确认 | 连续 `max(3, FRAME_LENGTH)` 帧确认 | 底牌可缺失或只识别一两张，不能放宽成 16/18 张开局 |
| 校准后跟踪 | 开启试验路线时使用固定 640×640 拼图 | 仍包含全宽桌面带、每帧手牌及存在时的底牌候选，不是三个贴着上一手牌的小框 |
| 拼图不可靠或定期复查 | 同一原图整图检测 | 计入两次调用成本，不能假装只有一次推理 |
| 本局结束 | 保留上一局统计，整图等待下一组新手牌 | 不控制游戏按钮，完整新手牌稳定后才替换显示 |

第二行通常向下展开，因此保留到手牌上沿的完整桌面带；不能只覆盖上一手单行的紧框。手牌减少也参与本家出牌归属，因此暂不降频或永久丢弃手牌区。

固定 640×640 指拼图图像尺寸。PyTorch/动态后端使用 640 方形模型输入；旧静态 ONNX/TensorRT 仍服从已有导出尺寸，如果导出为 960，则后端会按 960 运行，不会因拼图变为 640 就自动减少网络计算量。新训练/导出模型应明确提供 640×640 输入版本。

## 建议下一次训练什么

先训练 **YOLO11n 检测模型，`imgsz=640`，以 640×640 拼图作为主要部署目标**，保留现有牌类映射及标注语义。模型类别顺序必须与 `YOLO_TO_CARD_MAPPING`、权重中的 names 一致；无需为了参考 APK 而改成它的 28 类红黑分类。

这是接下来建议评估的独立候选，不代表已经训练、默认切换或验证能达到手机 200 ms。当前继续使用用户选择的现有权重。

同一份 YOLO11n 权重可覆盖整图、裁剪和拼图，前提是数据覆盖这些输入形态并验证精度；无需因为“拼过图”就必然改用另一种网络。是否额外训练专用小图模型，由同图对比决定。

YOLO11n 官方检测规格约 260 万参数，YOLO11s 约 940 万，n 更适合先建立手机速度基线。表中公开速度来自其指定硬件，不能直接当作本机安卓整轮性能：[Ultralytics YOLO11](https://docs.ultralytics.com/models/yolo11/)。

输入尺寸建议顺序：

1. **先验证 640×640。** 建立开局完整张数、三家跨行归属和切口去重的准确率基线。
2. **再对同一验证集测试 320×320 或 512×512。** 观察最小牌角、10、大小王、暗淡画面和跨行末张是否漏检；不能只比较 FPS。运行时代码本次仍固定 640，不会自动切到 320。
3. **较大整图回退单独评估。** 调整导出尺寸需要匹配后端和恢复契约，不能仅改文件名或把固定模型当动态模型用。

## 训练样本应怎样准备

- 保留原始整图样本：当前开局校准和整图回退仍需要它们。
- 增加裁剪与拼图样本，调用同一规划、保护宽度、统一缩放、114 灰填充及坐标映射；只做四图 Mosaic 不能代替真实部署拼图。
- 每个原始标注先与裁片求交，再通过对应 `Tile.project()` 变换，最后除以 640 得到训练所需归一化坐标。同一物体在两个图块中完整出现，就在两个位置分别标注，部署后再按原图坐标去重。
- 对切断的残片制定一致的可见性/裁切标注策略；不能将明显可见的牌角无标注地当背景，也不能把裁片外的完整框直接搬进画布。含糊难辨的残片可过滤相应训练样本，验证集仍保留切口困难案例。
- 切分训练/验证/测试应先按原始对局或录屏来源完成，再派生裁剪和拼图。同一原始帧的整图、不同重叠裁片或相邻近重复帧不应跨集合，避免虚高分数。
- 覆盖 17/20 张、中心切口、重叠副本、多个同点数、三家一行/两行、第二行末张、长牌组、空区、不同窗口比例、动画、变淡和缩放。按每个窗口及图块的最小牌角尺寸检查可读性；640 并不自动保证小目标足够大。
- 当前工具只提供几何映射和合成示意，**尚未实现批量训练集转换/导出工具，也没有启动训练**。正式训练前先抽样可视化复核转换后的标注。

Ultralytics 的训练和预测尺寸/填充规则见 [训练文档](https://docs.ultralytics.com/modes/train/) 与 [预测文档](https://docs.ultralytics.com/modes/predict/)。预处理实现若与训练数据生成方式不同，应单独做同图一致性检查。

## 参考 APK 的已确认信息

包内 `bundled_packed_strategy.json` 的 `full_fallback` 名称明确为 `yolo11n-300e-rect-datav3`，输入宽 1280、高 640，FP16；这是整图回退路线。两个拼图路线名为 `combine-320`、`combine-640`，对应 320×320、640×640、FP32，架构标注 YOLO11；没有仅凭文件大小把这两个路线断言为 n 或 s。

这是所分析 APK 的包内静态配置，实际手机可被运行时模型更新覆盖，不能代表所有版本或设备的实际选择。此工程不包含第三方权重、反编译源码或脚本。

1280×640 约 82 万像素，小于 960×960 的约 92 万；640×640 约 41 万，320×320 约 10 万。像素数只用于理解输入规模，不能直接按比例预测手机耗时。

## 验证要求与当前缺口

- 本次实现由纯几何、真实 Controller/Tracker 替身集成和既有实测框回归验证；合成图不证明真实检测精度。
- 需要人工标注真实同图与完整对局，检查漏牌、重复扣牌、切口回退比例和自动换局时序。中途恰剩十七张且出牌均消失时，仅靠牌框仍难确定是否完整开局，应在开局前启动。
- 未知地主身份无法安全判零时，保留未知；如果底牌持续显示、没有全图清空且关键出牌漏记，仍可能需要手动重置。
- Windows CPU 烟雾、CUDA、TensorRT、Android GPU/CPU 的结果分开记录。未完成真机整轮、发热和持续运行测量前，不承诺 200 ms。
