## 2. 问题来源与证据边界

用户提供的 Android 性能截图中，模型为 YOLO11s，捕获尺寸为 1080×2400；14 个已处理帧的平均预处理约 293.60 ms、推理约 871.79 ms、后处理约 18.23 ms，布局与发布约 0.75 ms，已计时阶段合计约 1184.37 ms，发布帧龄约 2121.12 ms。

这些是手机端的小样本结果，不是 Windows 基线。帧龄与阶段合计相差约 936.75 ms，现有数据无法区分像素复制、等待和调度各占多少；帧龄也不是物理屏幕已经显示的时间。200 ms 采样间隔不代表能在 200 ms 完成识别。

第三方静态分析报告位于 `E:\ongoing_projects\template-android\artifacts\apk-analysis\analysis-report-zh.md`。抽查可读源码和配置，确认存在：

- 有效区域打包规划：尝试 320 画布，再尝试 640，再尝试缩小，无法容纳则整图回退。
- 图块原图位置与拼图位置记录；原生拼图、颜色候选和白色连通区域检测接口。
- TFLite GPU、MNN OpenCL 与 CPU 候选配置，以及初始化失败回退。
- 预处理 Bitmap 复用、Canvas 缩放和有界队列丢弃旧图。

这不证明第三方在目标手机上实际启用了 GPU，也不证明其速度、准确率或全部业务流程。原生内部实现、部分加密脚本及部分反编译失败的方法仍不可见。

## 3. 已选方案：中心切分、切口重叠保护、原图坐标去重

### 用户确认的选择

用户接受切口保护方案：切分时让左右图块在中间共享一段图像，映射回原图后去重。相较于每次换切口、多次模型调用，优先验证此方案；不能在实测前声称计算开销必然更低。

对于宽为 W、切点为 c 的手牌长条，重叠保护范围设为 h：

```text
左图：原图横向 [0, c+h)
右图：原图横向 [c-h, W)
两图共享：原图横向 [c-h, c+h)
```

边界需要裁剪到合法图像范围。图块可上下排列，再等比例缩放、补背景；不能强制把宽高分别拉满。

### 保护范围与失败处理

- h 应依据模型实际识别的完整牌面标记宽度、尺度和截图清晰度确定，不先固定为某个像素数。识别目标可能是牌角标记，而非整张扑克牌外框。
- 如果共享区的实际宽度足够覆盖目标及必要上下文，跨越中心切点的目标就有机会在至少一个图块中保持完整；不能保证任意尺度都适用。
- 检测框触及图块切边、两块对同一位置给出冲突类别，或牌数不合法时，标记为不确定，扩大重叠、补查原图切口带或回到完整手牌输入。
- 每块记录原图裁剪框、拼图放置框、缩放和填充参数，以及同一原始帧的标识。先还原到同一原图坐标，再执行跨块去重与现有布局分析。
- 去重综合原图位置、类别、重叠程度和边界完整性；不能只按牌点或完全相同的浮点坐标判断。两张不同位置的 A 必须保留两张。
- 对同一位置类别冲突，不可直接保留一个就当成可靠结果；临近的相同牌点也不能因距离近而被合并。
- 切分和拼接增加边缘效应，训练、验证要包含实际生成的拼图，检查背景间隔、填充颜色与目标尺度。

### 备选：错位切口复查

用户另提出先从中心切分，下一次改变切点，让原切口附近的目标完整出现。此思路保留为补查候选，不作为当前优先路径。

需要合并两次识别结果时，优先使用同一张截图，避免发牌、叫地主拿底牌或出牌动画使相邻帧的牌面发生变化。不能把不同时间的局部结果直接拼成一手初始牌。额外调用必须计入整轮耗时。

## 4. 候选发现与正式开局确认分开

- 用户最初提出扩大 17/20 张判断范围，容忍切图造成的一两张误差；讨论后接受正式初始化不能放宽的原则。
- 允许在“发现手牌候选、触发进一步检查”阶段评估较宽范围，具体区间尚未确定。
- 自动模式正式初始化仍要求连续稳定的完整 17/20 张手牌、三张底牌、牌面多重集合法及尚无出牌的证据，沿用现有阈值和统计口径。
- 张数正确只是必要条件：即使识别出 17 张，也可能存在某张类别错误，仍要检查连续稳定与牌点上限。
- 真实 17 张只识别到 16 张时，不能仅靠允许 16 张来正确扣牌，因为不知道漏的是哪张。不能猜牌补齐或用错误多重集初始化。
- 真实 17 张重复识别为 18 张，应先依据空间位置消除重复；18 张也可能是 20 张漏检，不能只凭数量作决定。

## 5. 分阶段、分区域识别的候选设计

以下是讨论中的完整设计，并非全部已实现；V4.3 仅接入整图校准、保守候选拼图和整图复查，手牌继续逐帧检测：

| 阶段 | 主要输入 | 目的与约束 |
|---|---|---|
| 等待开局 | 优先扫描下方手牌候选 | 本家在下是当前布局先验；不能据此认定已完成开局 |
| 确认开局 | 同一截图中覆盖手牌、底牌和相关出牌区的输入 | 检查完整开局，避免把叫地主、发牌中或中途牌局当成起点 |
| 正常记牌 | 三家出牌区合拼，争取一次模型调用 | 优先保证短暂出牌和空区过渡可被观察 |
| 低频复查 | 手牌及必要的整图 | 提供本家出牌证据、检查新局和参照是否失效；周期待实测 |
| 不确定或布局变化 | 扩区或整图回退 | 保守停止确认，避免错误扣牌 |

本家初始手牌只扣一次；后续本家出牌只记录，上家和下家确认出牌才扣减。减少手牌检测前，必须改造依赖手牌可见性和手牌变化证据的布局流程，而非直接删除输入区域。

未检测、被裁掉、遮挡或不确定的区域均不能作为“已观察到空区”；否则会破坏连续相同出牌的空帧过渡规则。降频也不能造成连续确认长期无法达成。

## 6. 两行出牌与不对称余量

- 按用户观察的目标游戏，第二行主要出现在第一行下方，整体向上移动较少。因此三家出牌候选区向下多留余量，向上少留但不归零。
- 余量按实际牌面尺度和最大牌组测量，覆盖单张、长牌组和两行牌组；不宣称适用于所有软件。
- 优先整组裁剪；外围设置轻量检查，发现原区域之外疑似目标时扩区。不能只依赖已经被裁剪的小图模型发现被裁掉的第二行。
- 识别后映射回原图，再沿用或完善按行聚组、跨行合并和整组归属。拼图中的左右位置不代表原图中的玩家身份。
- 同一手牌由一行重排为两行不能重复扣减；右家短末行不能被错分到本家。保留现有真实框回归与独立本家证据保护。

## 7. 模型、输入尺寸和图像处理

- 整图、裁剪图和拼图不必分别训练模型。优先评估一份小模型权重，并让训练数据覆盖实际输入形态；双模型是否值得由实测决定。
- 一份训练权重可导出不同静态输入尺寸；动态输入依赖导出格式、执行后端和代码契约，并非任意文件都支持。
- YOLO11n、640 输入是先前提出的候选，不是最终默认配置；320/512 与较大整图回退输入都需要准确率和性能验证。
- 图像面积减半但仍填充到相同模型输入尺寸，不意味着网络计算量减半。减少模型实际输入或调用次数，才可能明显减少这部分计算。
- 以假设的 2400×540 长条为例：完整缩到 640 画布，有效内容约 640×144；切成两块并上下拼为 1200×1080，再缩到同一画布，有效内容约 640×576。牌面比例未变，但切口保护会增加少量内容和空间占用，需要重新计算布局。
- Windows 当前使用 PIL/Ultralytics 等图像链路；Android Kotlin 逐像素预处理的耗时不能直接归因到 Windows。评估窗口截图、图像转换、缩放、内存复用和复制次数，避免为复用而额外增加复制。
- Android Canvas、GPU/NPU 接入留待后续平台适配；Windows 验证主要复用几何算法、输入契约和牌局回放证据，不将电脑 CUDA 成绩当作手机性能。

## 8. Windows 验证与后续实施顺序

1. **记录当前基线。** 同一模型、设备、图片序列和配置下，测截图、图像转换、候选查找、裁剪/拼图、模型调用、坐标还原/去重、布局记牌和 UI 整轮耗时。GPU 异步执行要明确同步和计时口径，模型预热与首次加载分开统计。
2. **先做纯几何原型。** 中心重叠切分、等比例拼接、坐标往返和跨块重复消除可独立于 Qt、模型和业务测试；未通过前不替换当前整图链路。
3. **同图比较。** 当前整图路线作对照；比较实际标注而非将当前模型当成绝对真值。记录漏检、误检、重复框、类别冲突和切口目标完整性。
4. **完整牌局回放。** 覆盖开局 17/20 张、切口穿过 10/大小王/普通牌、多个同点数、左右家一行变两行、短末行、本家附近独立出牌、稳定空区、重复出同牌、遮挡、新局、窗口尺寸改变和模型切换。
5. **再接入阶段调度。** 高频三家出牌、低频手牌复查、外围检查、扩区和回退要验证时序，不能只测静态图片。
6. **最后评估训练与移植。** 几何算法成立后决定模型训练数据、输入尺寸和后端；安卓仍需单独完成同图一致性、真机整轮、发热与持续运行测试。

报告至少包含 mean/P95、预热条件、模型哈希、实际输入、调用次数、回退比例、丢帧与识别/记牌正确性。拼图额外成本、候选查找成本和补查成本全部计入，不能只展示小图模型前向时间。

200 ms 是用户提出的手机单帧整轮目标，目前未验证可达；不是 Windows 已有指标，也不等于连续多帧确认出牌的延迟。
