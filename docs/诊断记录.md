# 诊断记录与性能边界

[文档目录](README.md) · [排查与验证](排查与验证.md) · [配置参考](配置参考.md)

## 日常运行与完整诊断

日常日志自动启用，只记录服务启动/退出、设置命令、错误和牌局状态变化，不按每帧写图片。路径为运行目录的 `logs/runtime.jsonl`，按大小轮转，当前文件加四份历史，每份阈值10 MiB。旧日志自动替换，不会随运行时间无限积累；这是磁盘文件，与内存队列不同。

“设置 → 高级设置 → 完整诊断”默认关闭。开启后，推理子进程创建一个持续工作的后台保存线程；截图、模型推理和记牌仍在原推理线程执行。关闭后请求收尾，开启新会话前必须等旧线程结束。偏好通过后端回执与原子保存持久化，重启应用会按保存偏好启用；实际后台状态另行显示，开关为“是”不代表磁盘故障后仍在记录。

终端调试输出、实时YOLO输入预览和完整诊断独立。完整诊断是唯一的图片持久化入口，从开启时就开始，不需要先满足开局条件。

## 每帧材料

所有诊断材料仅保存在本机 `diagnostics/session_<UTC时间>_<随机标识>/`，默认不会上传或进入Git：

```text
manifest.json                         会话状态、完成度、环境与丢失起点
events.jsonl                          帧索引、解释码与异常
frames/00000001/
  original.png                        原始窗口截图
  call_01_input.png                   第一次实际传入YOLO接口的图
  call_01_input_annotated.png         这次调用的输入坐标标注
  call_02_input.png                   有复查/回退时才存在
  call_02_input_annotated.png
  final_original_annotated.png        最终结果还原到原图坐标后的标注
  frame.json                         当帧完整结构化证据
```

这里的“输入”指传给YOLO接口的RGB图片，可能是拼图或原图；不是模型内部归一化、填充后的张量。每次调用前先冻结输入，避免拼图画布复用或异常后的回退覆盖首个输入。后台只接收PIL副本和CPU数值，不接收GPU张量、模型对象或Qt对象。标注图由后台绘制，文字使用模型原始类别；牌点映射在JSON中保留。

`frame.json` 的schema为 `han-diagnostic-frame/v1`，包含：

- 进程内递增的frame_id、请求request_id/generation、UTC时间和单调时钟；不会按牌局重置帧号。
- 当前模型、实际载入文件路径、设备、各调用后端标志（PT/ONNX/TensorRT/FP16等）、阈值、牌类映射和所选布局；不会复制全部用户布局。权重与实际载入文件SHA是后台写入时磁盘文件的哈希，并不保证权重文件后来未被替换，或当前内存模型与文件字节完全相同。
- 每次模型调用的实际输入尺寸、拼图片段变换、检测框/类别/置信度、返回是否可靠、耗时和异常；拼图失败后的整图调用分开保存。
- 最终原图检测框、几何分区、当帧区域牌面、哪些区域已知、实际路线与布局状态。
- 更新前后状态、剩余牌、完整出牌历史、原始首次手牌、已确认漏检补扣/计数冲突、确认缓存、空区过渡和底牌缺失累计。
- 观察到的局序号round_id；中途接入已开始牌局时可能为0。它用于关联诊断，不参与判定开局或结束。
- 只读解释码：未知结果、底牌区域未知、底牌缺失暂停、连续确认进度、开局、首次扣牌、开局漏检补扣/冲突、历史变化、剩余牌变化和等待下一局。解释从实际前后状态推导，不替代业务判断，也不推测模型漏检原因。

会话manifest使用 `han-diagnostics/v1`；记录Python、系统、已加载关键包版本。源码目录可用Git时记录启用时HEAD，未打包进Git的源码修改仍可能存在，不能将HEAD当成整个运行环境的完整哈希。

## 有界保存与故障处理

| 对象 | 当前限制 | 达到限制时 |
|---|---|---|
| 待保存帧数 | 8帧，包含后台正在写入的一帧 | 暂缓采样，降到最多4帧且有足够内存后自动恢复 |
| 待保存图像与JSON预算 | 64 MiB，保守按每像素4字节加1024字节估算，复制前预留 | 不复制超预算内容，暂缓采样，余量足够后自动恢复 |
| 单帧JSON | 256 KiB | 暂停并报告材料不完整 |
| 全部诊断文件 | 1 GiB | 优先删除最早已结束且带本项目标记的会话 |
| 当前/异常未封口会话 | 不自动删除 | 无安全可清理空间时暂停诊断 |

64 MiB限制的是待保存RGB像素和冻结JSON的预算，并非整个应用的进程内存上限。Python对象、模型、业务截图及后台单张图片的编码/标注工作缓冲另有开销。队列包含正在写的一帧，避免“出队后仍占内存却不计数”。

容量清理只由保存线程执行，只删除专用目录中schema匹配、状态为closed/paused/failed的旧会话，保护当前会话、未结束的崩溃材料及未知目录。当前会话本身到达上限也会暂停，不覆盖同一会话早先证据。目录大小按单个应用实例管理，多个实例共用同一输出目录的争用未验收。

队列积压/总快照内存不足时只暂缓诊断采样，保存线程继续消化已接收任务，识别继续。低水位为最多4帧待完成，同时必须有足够字节容纳上一帧估算；恢复自动进行，不需要关开。暂缓期间跳过的检测帧会写入events.jsonl，record_type为gap、first_frame/last_frame为包含首尾的区间；状态显示主动跳过数，任意缺口使会话complete保持false。区间元数据由后台写入，最近8个区间用于状态显示；未写区间最多128段，无法及时记录会明确停止诊断，不静默截断。

磁盘/权限/快照格式错误、单个完整帧本身超过64MiB等无法靠排空队列解决的故障，仍保持暂停并提示；排除原因后关闭再开启会创建新会话。即使隐藏普通布局提示，暂缓和故障仍可见。日常日志本身写入失败会保持可见告警，修复目录后需重启识别服务重新建立日志处理器。`first_missing_frame`、已保存数量和完成度明确标记缺口；不会把缺帧会话称作完整。

帧先写入 `.pending_*`，材料写完才发布为正式帧目录；索引随后追加。会话收尾后才可能标为complete。关闭设置开关最多等待250 ms，进程退出最多等1秒；超时、强制结束或断电可能留下未封口材料。原子发布并不代表已经做了磁盘持久化屏障，不能承诺断电后所有最后写入都存在。

## 性能与使用建议

后台线程承担PNG压缩、绘制标注、文件写入、哈希与容量清理。主推理线程仍需复制图片、把检测结果转到CPU、复制状态及编码JSON；后台也会争用CPU和磁盘。因此线程能减少同步等待，但不能保证完全不影响识别速度。

性能提示新增“诊断快照”计时，包含图片复制、CPU结果提取与状态冻结；它与部分流水线阶段重叠，不应直接相加。“子进程整轮”沿用原流水线口径，主界面标题栏往返耗时还包括通信与轮询。常态运行保持完整诊断关闭，复现问题时短时间开启。

具体本机对照见[验证记录](排查与验证.md)。静态图、CPU、本地磁盘测量不能证明GPU、真实游戏连续运行、慢磁盘或手机上的固定开销。

反馈问题时先关闭并等收尾，查看manifest是否完整，再复制对应会话目录，附程序版本、操作步骤、预期结果和出现问题的帧号。图片可能含账号、昵称及其他屏幕信息，分享前自行检查。当前没有一键打包导出或自动回放器，完整材料也不能自动证明业务算法正确。

## 换局与清理的区别

64MiB是RAM待写快照，不是磁盘历史。每帧成功写入或取消后就释放名额和内存；已写PNG不会为下一局重新全部读回RAM。8帧限制不等于只存8张图片，一个检测帧通常有4张或更多图片。

开始下一局不会删除上一局。只要完整诊断一直开着，多局在同一session内连续编号；round_id区分牌局。关闭重开、重启识别进程会建新session，已有材料先保留。只有下一次写入即将使diagnostics总量超过1GiB，才按时间清理已结束的旧session，直到有空间。不是每开一局就删除，也不是保留最近3局。

当前session、异常未封口session和未知目录不自动删除。因此当前单个session达到1GiB，或所有剩余材料都不可安全清理时，会因磁盘配额暂停；这与队列暂缓自动恢复是不同情况。需先导出/处理旧文件，再关闭重开。详见[本次故障回归](V4.3.2问题回归与诊断机制.md)。
