# 诊断记录与性能边界

[文档目录](README.md) · [排查与验证](排查与验证.md) · [配置参考](配置参考.md)

## 日常运行与完整诊断

日常日志自动启用，只记录服务启动/退出、设置命令、错误和牌局状态变化，不按每帧写图片。路径为运行目录的 `logs/runtime.jsonl`，按大小轮转，当前文件加四份历史，每份阈值10 MiB。旧日志自动替换，不会随运行时间无限积累；这是磁盘文件，与内存队列不同。

“设置 → 高级设置 → 完整诊断”默认关闭。开启后，推理子进程创建一个持续工作的后台保存线程；截图、模型推理和记牌仍在原推理线程执行。关闭后请求收尾，开启新会话前必须等旧线程结束。偏好通过后端回执与原子保存持久化，重启应用会按保存偏好启用；实际后台状态另行显示，开关为“是”不代表磁盘故障后仍在记录。

终端调试输出、实时YOLO输入预览和完整诊断独立。完整诊断是推理运行证据的唯一图片持久化入口，从开启时就开始，不需要先满足开局条件。手动布局编辑器另有本机参考图缓存（config/layout_previews/，每布局名仅最新一张），用于重开编辑，不属于诊断会话或其磁盘额度，也不会进入推理流程。

## 每帧材料

所有诊断材料仅保存在本机 `diagnostics/session_<UTC时间>_<随机标识>/`，默认不会上传或进入Git：

```text
manifest.json                         会话状态、完成度、环境与丢失起点
events.jsonl                          会话总索引、缺帧区间及旧局清理记录
waiting/round.json                    首次开局前的等待段
waiting/frames/...                    开局前证据
game_0001/round.json                  第一局采集段标记
game_0001/frames/00000001/
  original.png                        原始窗口截图
  call_01_input.png                   第一次实际传入YOLO接口的图
  call_01_input_annotated.png         这次调用的输入坐标标注
  call_02_input.png                   有复查/回退时才存在
  call_02_input_annotated.png
  final_original_annotated.png        最终结果还原到原图坐标后的标注
  frame.json                         当帧完整结构化证据
game_0002/round.json                  下一局开始后新建
game_0002/frames/...
```

这里的“输入”指传给YOLO接口的RGB图片，可能是拼图或原图；不是模型内部归一化、填充后的张量。每次调用前先冻结输入，避免拼图画布复用或异常后的回退覆盖首个输入。后台只接收PIL副本和CPU数值，不接收GPU张量、模型对象或Qt对象。标注图由后台绘制，文字使用模型原始类别；牌点映射在JSON中保留。

`frame.json` 的schema为 `han-diagnostic-frame/v1`，包含：

- 进程内递增的frame_id、请求request_id/generation、UTC时间和单调时钟；不会按牌局重置帧号。
- 当前模型、实际载入文件路径、设备、各调用后端标志（PT/ONNX/TensorRT/FP16等）、阈值、牌类映射和所选布局；不会复制全部用户布局。权重与实际载入文件SHA是后台写入时磁盘文件的哈希，并不保证权重文件后来未被替换，或当前内存模型与文件字节完全相同。
- 每次模型调用的实际输入尺寸、拼图片段变换、检测框/类别/置信度、返回是否可靠、耗时和异常；拼图失败后的整图调用分开保存。
- 最终原图检测框、几何分区、当帧区域牌面、哪些区域已知、实际路线与布局状态。
- 更新前后状态、剩余牌、完整出牌历史、原始首次手牌、确认缓存、空区过渡和底牌缺失累计。
- 观察到的局序号round_id；0为尚未观察到开局，正整数对应game_0001等目录。它只关联诊断，不参与判定开局或结束。
- 只读解释码：未知结果、底牌区域未知、底牌缺失暂停、连续确认进度、开局、首次扣牌、历史变化、剩余牌变化和等待下一局。解释从实际前后状态推导，不替代业务判断，也不推测模型漏检原因。

按用户要求，基于本家出牌的事后补扣已撤回，当前诊断不再发布对应修正字段与解释码。旧版本已保存的历史材料保持原样，仅表示当时版本的行为。

会话manifest使用 `han-diagnostics/v1`；记录Python、系统、已加载关键包版本。源码目录可用Git时记录启用时HEAD，未打包进Git的源码修改仍可能存在，不能将HEAD当成整个运行环境的完整哈希。

## 有界保存与故障处理

| 对象 | 当前限制 | 达到限制时 |
|---|---|---|
| 待保存帧数 | 8帧，包含后台正在写入的一帧 | 暂缓采样，降到最多4帧且有足够内存后自动恢复 |
| 待保存图像与JSON预算 | 64 MiB，保守按每像素4字节加1024字节估算，复制前预留 | 不复制超预算内容，暂缓采样，余量足够后自动恢复 |
| 单帧JSON | 256 KiB | 暂停并报告材料不完整 |
| 全部诊断文件 | 默认1 GiB，可设置0.1–1024 GiB、最多两位小数 | 清理已封口旧会话，或当前会话已封口旧局 |
| 当前局/异常未封口/未知材料 | 不自动删除 | 无安全可清理空间时暂停诊断 |

64 MiB限制的是待保存RGB像素和冻结JSON的预算，并非整个应用的进程内存上限。Python对象、模型、业务截图及后台单张图片的编码/标注工作缓冲另有开销。队列包含正在写的一帧，避免“出队后仍占内存却不计数”。

在“设置 → 高级设置 → 诊断磁盘上限”填写额度，保存后重启仍生效。单位GiB（1024³字节），不是预占空间；作用于整个diagnostics目录，而非每局各分配一份。内存64MiB、8帧名额和256KiB单帧JSON不随此值扩大。

容量扫描及清理只由保存线程执行，按时间处理schema匹配且状态为closed/paused/failed的旧会话；当前会话只清已经封口的waiting/旧局，保护正在记录的局。异常未封口、未知目录及链接目标不自动删除。缩小额度后在后台下一次检查执行清理；当前局或受保护材料无法容纳则暂停，调大额度后如已暂停，需关闭再开启。多个实例共用同一输出目录的争用未验收。

队列积压/总快照内存不足时只暂缓诊断采样，保存线程继续消化已接收任务，识别继续。低水位为最多4帧待完成，同时必须有足够字节容纳上一帧估算；恢复自动进行，不需要关开。暂缓期间跳过的检测帧会写入events.jsonl，record_type为gap、first_frame/last_frame为包含首尾的区间；状态显示主动跳过数，任意缺口使会话complete保持false。区间元数据由后台写入，最近8个区间用于状态显示；未写区间最多128段，无法及时记录会明确停止诊断，不静默截断。开局边界也使用最多128条的小型元数据队列，按帧顺序建立目录；即使整局图片被跳过，也保留saved_frames为0的目录标记及全局缺帧索引，不会把旧队列图片放进新局。

磁盘/权限/快照格式错误、单个完整帧本身超过64MiB等无法靠排空队列解决的故障，仍保持暂停并提示；排除原因后关闭再开启会创建新会话。即使隐藏普通布局提示，暂缓和故障仍可见。暂缓仅在标题栏显示“诊断暂缓”，悬停可看完整原因，恢复后回显布局状态；暂缓/恢复不展开底栏或改变窗口高度。真正暂停和日志写入错误也统一在顶部显示简短提示与悬停详情，主窗口不提供底栏。日常日志本身写入失败会保持可见告警，修复目录后需重启识别服务重新建立日志处理器。`first_missing_frame`、已保存数量和完成度明确标记缺口；不会把缺帧会话称作完整。

帧先写入 `.pending_*`，材料写完才发布为正式帧目录；索引随后追加。会话收尾后才可能标为complete。关闭设置开关最多等待250 ms，进程退出最多等1秒；超时、强制结束或断电可能留下未封口材料。原子发布并不代表已经做了磁盘持久化屏障，不能承诺断电后所有最后写入都存在。

## 性能与使用建议

后台线程承担PNG压缩、绘制标注、文件写入、哈希与容量清理。主推理线程仍需复制图片、把检测结果转到CPU、复制状态及编码JSON；后台也会争用CPU和磁盘。因此线程能减少同步等待，但不能保证完全不影响识别速度。

性能提示新增“诊断快照”计时，包含图片复制、CPU结果提取与状态冻结；它与部分流水线阶段重叠，不应直接相加。“子进程整轮”沿用原流水线口径，主界面标题栏往返耗时还包括通信与轮询。常态运行保持完整诊断关闭，复现问题时短时间开启。

具体本机对照见[验证记录](排查与验证.md)。静态图、CPU、本地磁盘测量不能证明GPU、真实游戏连续运行、慢磁盘或手机上的固定开销。

反馈问题时先关闭并等收尾，查看manifest是否完整，再复制对应会话目录，附程序版本、操作步骤、预期结果和出现问题的帧号。图片可能含账号、昵称及其他屏幕信息，分享前自行检查。当前没有一键打包导出或自动回放器，完整材料也不能自动证明业务算法正确。

## 换局与清理的区别

64MiB是RAM待写快照，不是磁盘历史。每帧成功写入或取消后就释放名额和内存；已写PNG不会为下一局重新全部读回RAM。8帧限制不等于只存8张图片，一个检测帧通常有4张或更多图片。

每次观察到Tracker从WAIT_BEGIN进入开局状态时切到新game_XXXX目录，开局首帧归新局。结束后到下一局开始前的帧继续归上一局；首次开局前存waiting。帧号在进程中连续递增，不按局重置。分局只跟随现有状态机，不改变开局、扣牌或结束逻辑。

round.json使用han-diagnostic-round/v1，记录局号、采集段封口状态、首末帧、保存数量，以及是否观察到开局/等待下一局。closed只表示该采集段已封口，不等于捕获了完整物理牌局或没有缺帧。中途开启诊断只能记录后半段；关闭重开、重启识别会创建新的父session，不拼接不同采集段。已有旧格式材料保留原样，不迁移。

开始下一局本身不会无条件删除上一局；当总量接近所设额度，或用户调小额度时，后台才清理可删除的最早旧材料。当前session中的已封口旧局也可清理；events.jsonl追加retention_cleanup记录，manifest记录pruned_rounds并标complete为false。索引可能保留已清理目录的历史路径，不能据此认定文件应仍存在。完整反馈材料应在停止后一起复制父session索引及相关局目录。

当前局、异常未封口材料或未知目录占满且无安全可清理空间时，会因磁盘配额暂停；这与队列暂缓自动恢复不同。先调大额度或自行处理旧材料，再关闭重开。磁盘检查留有少量元数据余量，当前写入失败会保留故障材料，不承诺文件系统分配空间或多个进程并发时的严格配额。详见[本次故障回归](V4.3.2问题回归与诊断机制.md)。
